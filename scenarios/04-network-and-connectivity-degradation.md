# Scenario 04 – Network / Connectivity Degradation

## Ticket

Users report intermittent connectivity to an application running on WEBVM-2. Investigate whether there is evidence of abnormal network activity or a network-related issue affecting the VM.

## Investigation Objectives

The objective is to determine whether the reported connectivity problems are associated with abnormal network activity on WEBVM-2.

The investigation focuses on:

•	Network traffic and throughput.

•	Packets sent and received.

•	Network packet errors.

•	Comparison with other VMs.

•	CPU, memory and disk activity that could affect VM responsiveness.

•	Application and system events.

•	Timing of the reported issue.

•	Whether the available Azure Monitor data is sufficient to identify the cause.

An important part of the investigation is to determine whether the issue is actually network-related or whether another VM-level problem is affecting the application’s connectivity.

## Lab Simulation

•	Application errors were generated to simulate connectivity timeouts.

eventcreate /ID 900 /L APPLICATION /T ERROR /SO WebApp /D "Connectivity timeout"

•	Network activity was generated by repeatedly downloading a Windows update package and deleting the downloaded file.

while ($true)
{
    Invoke-WebRequest `
        -Uri "https://catalog.s.download.windowsupdate.com/d/msdownload/update/software/secu/2026/08/windows10.0-kb5120249-x64_3519a66b88277af9104ea45839c6a5b6f47122f0.cab" `
        -OutFile "C:\Temp\test.bin"
    Remove-Item "C:\Temp\test.bin"
}

## Investigation

### 1. Identify available network performance counters

The available network-related performance counters were first reviewed.

Perf

| where ObjectName contains "Network"

| distinct CounterName

Relevant counters identified included:

•	Packets Outbound Errors

•	Packets Received Errors

•	Packets Received/sec

•	Packets Sent/sec

•	Bytes Total/sec

•	Bytes Sent/sec

•	Bytes Received/sec

•	Packets/sec

### 2. Investigate packet activity

The number of packets received and sent by WEBVM-2 was investigated to identify unusual network activity.

Perf

| where Computer == "WebVM-2" and CounterName == "Packets Received/sec"

| top 100 by bin(TimeGenerated, 2min)

| render timechart

![packets-sent-sec](../screenshots/scenario-03/packets-sent-sec.png)

Perf

| where Computer == "WebVM-2" and CounterName == "Packets Sent/sec"

| top 100 by bin(TimeGenerated, 2min)

| render timechart



### 3. Investigate network throughput

Bytes sent and received were reviewed to identify changes in network traffic.

Perf

| where CounterName in ("Bytes Sent/sec", "Bytes Received/sec") and  Computer == "WebVM-2"

| top 200 by TimeGenerated

| summarize max(CounterValue) by bin(TimeGenerated, 2m), CounterName

| render timechart

![bytes-sent-received](../screenshots/scenario-03/bytes-sent-received.png)

The received traffic was also compared with other VMs.

Perf

| where CounterName == "Bytes Received/sec"

| where TimeGenerated > ago(2h)

| summarize max(CounterValue) by bin(TimeGenerated, 2m), Computer, CounterName

| render timechart

### 4. Check network packet errors

Packet error counters were investigated to determine whether there was evidence of packets being dropped or transmitted incorrectly.

Perf

| where Computer == "WebVM-2"

| where CounterName in ("Packets Received Errors", "Packets Outbound Errors")

| top 100 by TimeGenerated

### 5. Check other VM resources

During the investigation, WEBVM-2 also became noticeably laggy. CPU, memory and disk activity were therefore checked to determine whether the VM’s responsiveness could be related 
to a general resource problem rather than networking.

CPU usage was reviewed using average and maximum values over time.

Perf

| where Computer == "WebVM-2"

| where CounterName == "% Processor Time"

| top 200 by TimeGenerated

| summarize avg(CounterValue) by bin(TimeGenerated, 2m), CounterName

| render timechart

Disk queue length was also checked:

Perf

| where CounterName == "Avg. Disk Queue Length" and Computer == "WebVM-2"

| top 200 by TimeGenerated

| summarize max(CounterValue) by bin(TimeGenerated, 2m), CounterName

| render timechart

Available memory was reviewed as well:

Perf

| where Computer == "WebVM-2"

| where CounterName == "Available Bytes"

| top 200 by TimeGenerated

| summarize max(CounterValue) by bin(TimeGenerated, 2m), CounterName

| render timechart

### 6. Investigate Windows Events

Windows Event Logs were reviewed for errors and warnings occurring around the suspected incident.

Event

| where Computer == "WebVM-2"

| where EventLevelName in ("Warning", "Critical", "Error")

| where TimeGenerated > ago(2h)

| project TimeGenerated, Source, EventLog, RenderedDescription, EventID

## Findings

WEBVM-2 experienced a period of increased CPU and memory usage. Increased network activity was also observed during approximately the same period, including an increase in packets received.
The disk queue length did not appear abnormal during the same time period, and packets sent remained within the observed normal range.
When compared with the other VMs, WEBVM-2 showed higher received traffic. However, based on the available telemetry, it was not possible to determine that the observed
traffic was sufficient to cause a network throughput problem.
Packet receive and outbound error counters did not show evidence of network packet errors.
Several system and application warnings/errors were also identified during the investigation. These require further investigation, particularly within the application logs.

## Conclusion

The investigation identified abnormal network activity on WEBVM-2 during a period when the VM was also experiencing increased CPU and memory usage.
However, Azure Monitor telemetry alone was not sufficient to establish the root cause of the reported connectivity degradation. The observed increase in received network traffic could be related to the issue, 
but the available data does not establish a causal relationship.
Troubleshooting limitation: monitoring data can provide evidence of abnormal behaviour without necessarily identifying the underlying cause.

## Recommended Next Steps

Further investigation would include:

•	Investigating the application logs for the connectivity timeout errors.

•	Checking whether the issue affects specific sources or destinations or all network traffic.

•	Reviewing recently changed NSG rules.

•	Checking whether an NSG could be blocking or affecting the relevant traffic.

•	Checking whether the VMs are behind a Load Balancer or another network component that could contribute to the issue.

•	Using Network Watcher for further network-level investigation.

•	Performing basic Windows networking troubleshooting if appropriate.

•	Determining whether the connectivity issue affects the VM generally or only the application.

## Limitations

The scenario was simulated by generating network activity and application connectivity errors. The simulated workload does not reproduce a real application network failure.
The available Azure Monitor telemetry was useful for identifying changes in network activity and comparing the affected VM with other VMs, but it was not sufficient to establish the root cause of the connectivity problem.
